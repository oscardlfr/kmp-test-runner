# Evidence3 agentic benchmark — Claude Code vs Codex CLI, with and without kmp-test, on a multi-module test-failure task

Campaign completed 2026-10-02 (window 2026-10-01T21:30:31Z – 2026-10-02T00:59:14Z, all times UTC).

**This is the campaign's second attempt.** The first attempt (`4e228608-ec59-44f5-9ddc-a40a33186ca4`, started 2026-10-01 at 17:41Z, same commit, design, scenario, prompts and timeouts) ended with a failed run state: 19 provider sessions completed, one Codex CLI session timed out, and the last six rounds of both runtimes could not start because the host's elevated orchestration runner crashed. Under the preregistration nothing from that attempt is analyzed or published, and amendment A4 allowed this one re-run, unchanged. This attempt also ended with a failed run state, because one session was lost to a failed guest call; amendment A5, decided before any result of the attempt was read, treats such a loss as missing data, like a rejected cell, and lets the campaign stand (see Threats to validity and Reproducibility and availability).

## Summary

**Primary metric.** Key facts (the answer block's outcome kind, failing modules, failing test classes and failing-test count all correct) matched in 28 of 30 campaign sessions: Claude Code with kmp-test 7/8, without 7/7; Codex CLI with kmp-test 7/8, without 7/7. Of the 2 sessions that did not match, 2 had the failing-test count wrong. 7 of the harness's 10 states finished PASS (BrokerReady to LiveAuthorized); LiveRunning ended FAIL only because one session was lost to a failed guest call, which amendment A5 treats as missing data, and the last two states did not run (the orchestrator's failure-safe closure copied the evidence). 30 of 32 sessions were accepted (1 rejected, 1 lost to a failed guest call), so each agent's free arm has 7 counted sessions against 8 in its product arm. The frozen infra-flake classifier flagged 3 of the 30 cells it could classify (claude-code-14, codex-cli-4, codex-cli-14); the Sensitivity table in Results excludes them and the primary tables keep them. Amendment A2 had raised the infra-flake stop threshold from 3 to 6 cells before any campaign session; at the original threshold of 3 this result would have stopped the campaign and published nothing.

**Efficiency (median per session, with kmp-test vs without).**

- Claude Code · claude-sonnet-5 reported the key facts correctly in 7/8 sessions with kmp-test and 7/7 without; Codex CLI · gpt-5.6-terra reported the key facts correctly in 7/8 sessions with kmp-test and 7/7 without.
- Claude Code (claude-sonnet-5) with kmp-test: median 3 tool calls vs 12 without, median wall-clock 4.0 vs 3.8 min (per-session range 3.4–5.2 vs 2.8–8.3 min; [breakdown](./README.md#results)), estimated API cost $0.08–$0.19 vs $0.15–$0.29 per session.
- Codex CLI (gpt-5.6-terra) with kmp-test: median 4 tool calls vs 20 without, median wall-clock 4.0 vs 5.0 min (per-session range 3.6–4.9 vs 4.3–6.7 min; [breakdown](./README.md#results)), estimated API cost $0.12–$0.22 vs $0.22–$0.42 per session.

Medians and ranges only: no ratio, no significance test, no "faster" or "better" wording (see "What this benchmark does NOT measure" below). Turns, tool calls and tool output are not the same quantity across the two agents, and cost is a list-price estimate from recorded tokens, not billing.

**Caveats.** `success` (key facts and at least one test command that ran; product arm only) was 7/8 for Claude Code and 7/8 for Codex CLI. n=8 per runtime and arm is not a statistically powered sample, and the task is one scenario, so this design cannot support a claim about any other task (see Limitations).

Known in advance (the preregistration's decisions D1 to D12 and its amendments A1 to A5, not placeholders):

- **Runtimes**: Claude Code 2.1.238 (`claude-sonnet-5`, reasoning effort `high`) and Codex CLI 0.154.0 (`gpt-5.6-terra`, reasoning effort `high`), both logged in with OAuth sessions inside the guest.

The agent must report the failing modules, the failing test classes and the failing-test count in a fixed answer block.
- **Design**: 8 repetitions per runtime per arm, counterbalanced `ABBA BAAB BAAB ABBA` on arm, 16 cells per runtime and 32 sessions in all; the runtime that goes first alternates every round. Preceded by a 4-session canary (one cell per runtime per arm), reported separately and never pooled into n. No retries and no cell replacement.

- **Product under measurement**: kmp-test-runner `0.16.0` at commit `c3da7be` (full SHA `c3da7bec808f0e43c91ddbf90f7e4bfc3ab7665a`), the same commit as the harness. The agents receive the skill snapshot of the `v0.15.0` commit.

## Scope

This document covers the Evidence3 canary and campaign results for one scenario, `multi-module-test-failures` (NowInAndroid, family `multi-module-tests`, tagged `held-out`: the skill and the product were not tuned against it). The agent is asked to run the unit tests of the 11 in-scope modules of a project whose production code was changed, and to report which modules and test classes fail and how many test methods. It is explicitly **not** a re-run or a superset of Evidence2: it is a different task (11 modules and 93 tests instead of one module and four test executions), a different harness commit, a larger sample (n=8 instead of n=4 per runtime and arm), and it states correctly what the evaluation guest holds (Evidence2's erratum E2). No cross-campaign comparison is drawn on any metric; the [detailed document](../../../docs/agentic-benchmark.md) shows both campaigns side by side, labeled as different tasks. It does **not** cover a coverage task on many modules, any other scenario, any platform other than Windows, or any agent other than the two named. It reports the canary (4 sessions, pipeline validation only, never pooled with campaign data) and the campaign (32 sessions) separately.

## Design

Full text: [`preregistration.md`](preregistration.md) §1 (Design), §4 (Models) and its Amendments section (A1 to A5). The decisions were locked before any live session; the amendments are dated, A1 to A4 were appended before the campaign attempt this document reports (A4 after the first attempt, which is not reported), A5 after that attempt's sessions had run and before any result of it was read, and none changes what a metric means. The sha256 of the preregistration as published is `b088c7aee6612107ed3f314286385f5a34a289c63aca0dcedf410bcbb225fdde`.

- Two runtimes, two arms, **one scenario** (D1), **n=8** per runtime and arm (D2): 16 cells per runtime, 32 sessions.
- Counterbalanced on two independent axes (D2): the arm order within each runtime, `[A,B],[B,A],[B,A],[A,B],[B,A],[A,B],[A,B],[B,A]` (A = product, B = free), and the runtime dispatch order, which alternates the first mover every round. Sessions run one at a time.
- **D3**: a 4-session canary (cells 0 and 1 of each design) checked the pipeline, the controls and the timeouts with real agents; it is never counted in n. The campaign is 32 sessions. No retries and no cell replacement.
- Reasoning effort `high` for both runtimes, pinned and recorded per cell, through two different mechanisms (a harness-pinned CLI flag for Claude Code, the model registry's default for Codex CLI); the two labels are provider-defined and are not claimed to mean the same effective thing.
- Spend and time limits (D6, D11): Claude Code ran with `--max-budget-usd 6`, a ceiling on plan usage priced with the CLI's own table, which prices `claude-sonnet-5` at 1.5 times the published list rates (Evidence2's erratum E1); Codex CLI has no budget flag. The provider timeout is 1800 s (clamp(3T + 600, 1800, 3600), with T the measured `kmp-test` duration of the provider-free smoke rounded up to seconds: 210 s in the sizing run and 209 s in this campaign's own smoke), the worker timeout 1860 s and the guest transport timeout 1920 s.
- The treatment (D7): the product arm receives the kmp-test skill and the `kmp-test` command, and a short wrapper before the prompt asks the agent to use the skill; the free arm receives the same prompt with neither. Both arms run under the same execution profile.

**What changed in the design since Evidence2** (each is a fact of the code at the deployed commit, not an interpretation): n=8 and the 8-pair designs; the multi-module family and its four-field answer protocol, graded by exact set and integer equality; auto memory off for Claude Code in both arms; five launcher variables and 30-minute Bash timeouts for Claude Code in both arms; the agent-state listing, the session ids and the transcript access scan; Codex CLI tool output measured from command output; the classifier support for compound, redirected and wrapped commands; and the corrected statement that the ground truth is on the guest and the control is detection by the scan (section 3 of the preregistration).

## Scenario

`multi-module-test-failures`, family `multi-module-tests` (D4).

- Project: NowInAndroid (`android/nowinandroid`), pinned commit `7d45eae4f8720a0c77f507712ba2437ff974b6ed`.
- The task: run the unit tests of every module except `:app`, `:core:designsystem`, `:feature:foryou:impl` and `:feature:interests:impl` (their Robolectric tests need network access the guest does not have; where a module has build variants, use demoDebug), then report the result in a fixed block (`KMP_EVAL_RESULT ... KMP_EVAL_RESULT_END` around a JSON object with `outcome_kind`, `failing_modules`, `failed_test_classes` and `failed_count`). The full prompt is in the preregistration.
- In scope: 11 modules with 93 unit tests in all (`:core:common`, `:core:data`, `:core:datastore`, `:core:domain`, `:core:navigation`, `:core:network`, `:feature:bookmarks:impl`, `:feature:search:impl`, `:feature:settings:impl`, `:feature:topic:impl` and `:lint`).
- The failure is injected by one committed patch (sha256 `5574b995a1f9fc62c5b1460461c2a59fccba1061619262a5489e89899c42147d`) that changes one line in each of two production files; the harness applies it, uncommitted, to each session's fresh worktree.
- Ground truth: `outcome_kind` `tests_failed`; failing modules `:core:data`, `:core:domain`, `:feature:bookmarks:impl`; failing test classes `BookmarksViewModelTest`, `CompositeUserNewsResourceRepositoryTest`, `GetFollowableTopicsUseCaseTest`; 6 failing test methods. Gradle on the host, twice on the unpatched project (93 tests, 0 failures) and twice on a fresh clone with the patch (93 tests, 6 failures, identical), and `kmp-test parallel` on the same patched project (same modules, classes and methods), established it; the provider-free guest smoke before the live sessions asserted the same values again.
- Known behaviors of the product on this scenario, found while establishing the ground truth and not changed: `kmp-test` dispatches test tasks for 27 modules, not only the 11 in scope, and its own count of dispatched tasks is not the number of tests; the coverage tasks of three modules without unit tests fail with "no tests were run", reported as `coverage_report_dispatch_failed`; and `kmp-test` 0.16.0 passes the string `undefined` as `ANDROID_SDK_ROOT` to Gradle when only `ANDROID_HOME` is set, which the harness avoids by setting both variables for every session.
- Tagged `held-out`.

## Methods

Sessions ran on harness commit `c3da7be` (full SHA `c3da7bec808f0e43c91ddbf90f7e4bfc3ab7665a`, as every record's `repo_commit` states), in a Windows 11 guest VM with a restricted network (provider APIs only), 4 vCPU and 12 GiB of memory. `claude-code` 2.1.238 (`claude-sonnet-5`) and `codex-cli` 0.154.0 (`gpt-5.6-terra`) both ran at reasoning effort `high`. Dispatch order alternated first-mover per round and arm order was `ABBA BAAB BAAB ABBA`, exactly as pre-registered (the first mover alternated between the two agents on all 16 pairs).

- **Isolation (D5)**: each session has a fresh git worktree with the patch applied, a fresh copy of the Gradle seed (warmed online once and certified offline, 96 Gradle tasks with `--offline`), a fresh home for the `kmp-test` process, a Windows job object with kill-on-close, and no provider session persistence. The guest also holds a full checkout of the deployed commit, including the corpus files and the harness's own test fixtures; nothing prevents an agent from reading them. The control is detection: every transcript was scanned after the campaign for six patterns (the corpus, the preregistration, the private-evidence directory, the harness's test directories, the answer fixtures and the campaign's private root). See the controls audit.
- **Agent state (D5)**: the agents' configuration directories were listed (path, size and modification time, never contents) before and after every session; a change to a file a later session would load is recorded as `agent_state_clean: false`.
- **Treatment texts (D7)**: the product-arm wrapper for Claude Code is a fixed directive that asks for the skill before any Bash call; for Codex CLI it is `$kmp-test-runner` and a blank line. The free arm receives the scenario prompt unchanged. Each cell records the hash of the prompt actually delivered and of the delivered skill content.
- **Metrics (D8, D9)**: key facts is the primary metric and the only one compared across arms: the answer block must be well formed and all four fields must match the ground truth (outcome by exact string, modules and test classes by set equality, the count by integer equality). `success` (key facts and at least one real test command ran) is recorded for both arms and reported for the product arm only. Secondary: tokens as each runtime reports them, `num_turns` (per runtime only), wall-clock, tool calls (for Claude Code every `tool_use`; for Codex CLI every `command_execution`), command kinds from the frozen classifier, and tool output bytes, labeled `tool_results` for Claude Code and `command_output` for Codex CLI.
- **Cost (D10)**: an estimate from recorded tokens at the list prices of the preregistration (`cost-estimate.mjs`), priced as a range because the records do not separate five-minute from one-hour cache writes and Codex CLI reports no cache writes; the point value is the midpoint.
- **Cell treatment (D12, amendment A5)**: accepted cells count in their arm's denominator, including wrong or missing answers; a rejected cell is never replaced and counts as declared, not counted, and so does a session lost to a failed guest call (reason codes `provider_runtime_real_worker_failed`, `guest_bundle_failed` and `provider_runtime_real_guest_bundle_call_failed`). The infra-flake classifier (frozen before the campaign; logic hash `f91985672fcc1df147f2b3e56c11ca104f870502dac8bba4e8ed524235590b0f`) flags two environment-fault signatures; the primary summary includes every cell and the sensitivity summary excludes the flagged ones.
- **Stop rules (preregistration §10, as amended)**: stop and publish nothing on 6 or more infra-flake cells, any transcript-scan hit, any accepted cell whose `agent_state_clean` is not true (with the A3 exception for Codex CLI's `config.toml`), 4 or more rejected or missing cells, or any state FAIL other than a LiveRunning FAIL caused only by sessions lost to a failed guest call (amendment A5). None held after the campaign: 3 infra-flake cells (stop at 6), 0 transcript-scan hits, 0 accepted cells with an agent state that is not true outside A3's exception, 2 rejected, missing or non-success cells (stop at 4), and no state failed other than the LiveRunning FAIL that amendment A5 explains.
- **Closure**: because LiveRunning ended FAIL, the states EvidenceCopied and Closed did not run. The orchestrator's failure-safe closure copied each cell's record and audit (and the rejection) from the guest; the raw transcripts of the accepted cells were then copied through the broker with their sizes checked against the records, and the analysis commands ran on that directory, from the deployed checkout as the preregistration (section 8) says. The published summaries (`campaign-summary.json` and `campaign-summary-sensitivity.json`) were then regenerated with this repository's `campaign-summary.mjs`, after a bookkeeping fix: a missing cell without a record is assigned to its design arm (the arm the manifest's `round_order` gives its position), where the deployed tool had grouped it with an unknown arm. The deployed tool's output is kept, and the only difference between the two is that cell's group: codex-cli round 7 is declared in the free arm and not counted, instead of forming a group of its own (no counted session, metric or key fact changed; the PR that publishes this record shows the field-by-field comparison). This is a declared deviation from running the analysis from the deployed checkout, limited to that accounting. No result was read before the stop rules had been evaluated, except that the cost estimator printed the per-cell token counts of the counted sessions to the operator's console before that (an operator mistake, disclosed in the controls audit; the stop rules do not use them).
- **Analysis commands**: `node tools/agentic-eval/campaign-summary.mjs <campaign-dir>` (primary and sensitivity), `node tools/agentic-eval/cost-estimate.mjs <campaign-dir>`, `node tools/agentic-eval/infra-flake-classifier.mjs <campaign-dir>`, `node tools/agentic-eval/transcript-access-scan.mjs <campaign-dir>` and `node tools/agentic-eval/evidence2-tables.mjs <campaign-dir>` (the Results tables of this document; never hand-edit between its markers).
- **Gate validation** (no-provider mechanism checks, not benchmark data): a provider-free run reached `Closed` with all ten states PASS (`23738e2e-5a14-4726-b184-e392ec294917`), and again after the harness fix of amendment A1 (`490d12dd-3a10-4786-9667-e8676b342a70`). The canary `09a176e3-6bfb-4bf7-a950-5dfcdc1d9935` accepted its four sessions; a first canary attempt (`7b0041b8-4299-4505-a480-b7cb02187fc8`) stopped at the provider-free smoke before any session because the guest's Gradle daemon died, and is not pooled with anything.
- **Host discipline**: the operator checked at launch that no other heavy workload (a build, compiler, Gradle, Docker or test process) was running on the host and started none during the campaign's live window. The host's Windows event logs between 2026-10-01T21:30:00Z and 2026-10-02T00:59:30Z show 7 application crash events (MicrosoftEdgeUpdate.exe 3, exception 0xc0000005, powershell.exe 3, exception 0xc0000005 and sppsvc.exe 1, exception 0xc0000005), 0 .NET runtime crash events and 0 corrected hardware error events (WHEA-Logger). The first attempt's window was not so quiet: another workload compiled native code on the same host; before this attempt the machine's owner stopped that workload and, as reported to the operator and not verified by it, disabled the CPU's turbo boost (see Threats to validity).

## What this benchmark does NOT measure

- **Generalization beyond this one scenario.** `multi-module-test-failures` only; no claim is made or should be inferred about either agent on any other task, scenario family or codebase.
- **A cross-runtime ranking or "winner."** The within-arm comparison of Claude Code and Codex CLI is descriptive only: medians and ranges, no significance test, no ratio, no "faster" or "better" wording, and `high` is a provider-defined label.
- **A cross-runtime comparison of `num_turns`, tool calls or tool output.** Claude Code counts assistant turns and every tool use and measures the tool results returned to the model; Codex CLI reports one turn per non-interactive session, counts only command executions and measures the command output as logged. They are different quantities, not the same quantity at different rates; where the repository README or a table puts the two agents' tool-call medians side by side, it is a descriptive listing of different counts, not a comparison of capability.
- **The agent's behavior outside the sessions' conditions.** Every session ran in a fresh worktree on a pinned project in a restricted-network guest, with permission checks bypassed; no claim is made about interactive use.
- **A comparison against Evidence2's numbers.** Different task, different sample size, different harness commit. See Scope.
- **Billing.** The cost figures are list-price estimates from recorded tokens for OAuth sessions, not invoices.

## Threats to validity

Full detail: the controls audit, published alongside this document as [`controls-audit.md`](./controls-audit.md) (read-only against the measured checkout at harness commit `c3da7be`). This section distills its findings.

- **A first attempt failed and the campaign was run again (amendment A4).** The first attempt (`4e228608-ec59-44f5-9ddc-a40a33186ca4`, started 2026-10-01 at 17:41Z) ended with its LiveRunning state FAIL at 20:48:53Z, after 19 provider sessions completed and one Codex CLI session timed out (a transport failure whose cause was not determined). The last six rounds of both runtimes could not start because the host's elevated orchestration runner crashed (access violations in the .NET runtime of Windows PowerShell); in the same window the host logged crashes of unrelated processes and corrected hardware errors, while another workload compiled native code on the same machine. The preregistration's stop rule (any run state FAIL) applied, so nothing from that attempt was analyzed or published, and its records and transcripts stay private and unread. To diagnose the failure, only the run receipt's per-session statuses, exit codes, failure reasons, start and end times and process-output sizes were read; no key fact, answer, token count, cost or tool-call count of it was looked at before amendment A4. The decision to run once more was taken without looking at any result, and amendment A4 fixed it before the second attempt began: the same commit, design, scenario, prompts, timeouts and stop rules, and no further re-run. What remains is a second draw of the same experiment, taken because of an infrastructure failure and not because of a result, on a host whose hardware may be unstable (see Host discipline in Methods for its event log over this attempt's window); the stop rules and the checks of the controls audit catch some effects of that (a flagged cell, a missing cell, a failed state) and not others.
- **A second attempt ended in a failed run state and stands under amendment A5.** Its harness states BrokerReady to LiveAuthorized finished PASS. LiveRunning ended FAIL at 2026-10-02T00:59:15Z, and its only failed session is codex-cli round 7, lost to a failed guest call after 6 min 4 s (reason code `provider_runtime_real_worker_failed`; the broker's response said the Hyper-V socket target process in the guest had terminated). The states EvidenceCopied and Closed did not run. claude-code round 8 was rejected by the harness's integrity checks (hook accounting, transcript structure and tool-result completeness: its transcript ended without a terminal result event). A5, decided before any key fact, answer, token count, cost or tool-call count of this attempt was read, gives its reason: the rule on run states was written for systemic failures, about one guest call in thirty failed on this host for reasons outside the agents during the two attempts while corrected hardware errors and crashes of unrelated processes were logged, any long campaign on this machine would be void under that rule, and the other 31 sessions of the attempt completed normally. A5 is a loosening of a pre-registered rule, made after the sessions had run and before their results were read; it changes no metric, keeps every other stop rule (2 rejected or missing cells here, against a stop at 4), and adds no re-run and no make-up session, which would add a temporal confound. Both missing cells fall in the free arm, so each agent's free arm has 7 counted sessions against 8 in its product arm, and the Sensitivity table can only lower them. The lost session's cause is not determined: the broker's response named a terminated Hyper-V socket target process in the guest, which a guest process crash or an action of the agent could both explain, and its evidence was not copied.
- **Environment flake: 3 of 30 classifiable cells flagged.** `infra-flake-classifier.mjs` classified every campaign cell with a transcript from its raw transcript (the two sessions without a record could not be classified). It flagged 3 cells (claude-code-14, codex-cli-4, codex-cli-14) and marked 2 unknown; the sensitivity summary excludes the flagged cells and keeps the unknown ones. Amendment A2 raised the stop threshold from 3 to 6 cells after one guest Gradle daemon death in about 11 heavy runs of the pre-run checks; it loosens a rule that was set before that data was seen, and it was appended before any campaign session. The result for this campaign (3 flagged cells) meets the original threshold of 3 and not the amended one of 6: the amendment decided the outcome.
- **The ground truth was on the guest; the control is detection.** The deployed checkout on the guest holds the corpus files and the harness's test fixtures, harness code on the guest reads the ground-truth file during a session, and the agent runs as the same user with permission checks bypassed. The pre-session isolation probe in the repository is called by nothing. The transcript scan, run after the campaign, matched 0 of 30 cells; that shows no transcript names the corpus, the preregistration or the private evidence, not that no session could have read them.
- **Agent state.** Claude Code: the listing showed no change to a context-relevant file in any of the 15 sessions. Codex CLI: in 15 of the 15 sessions (codex-cli-0, codex-cli-1, codex-cli-2, codex-cli-3, codex-cli-4, codex-cli-5, codex-cli-6, codex-cli-8, codex-cli-9, codex-cli-10, codex-cli-11, codex-cli-12, codex-cli-13, codex-cli-14 and codex-cli-15) the only context-relevant file that changed was `config.toml`, which Codex CLI rewrites at the start of every session (1369 bytes before every one of those sessions; only its modification time changes) and which the harness's `--ignore-user-config` makes Codex skip; amendment A3 counts these cells as clean, and `agent_state_clean` is false for them in `campaign-summary.json`. Codex CLI also updates `memories_1.sqlite` and other SQLite state files in its home in every session; they are outside the listing's context-relevant set, and the harness does not open them, so their contents are not verified (amendment A3). Claude Code's auto memory is requested off; the harness does not verify that Claude Code honors it, and the listing showed 0 entries under `projects/*/memory/`.
- **Exposure asymmetry** (`kmp_test_count` and `gradle_count` per runtime and arm, from this campaign's `campaign-summary.json`):

  | runtime | arm | kmp_test_count | gradle_count |
  |---|---|---|---|
  | claude-code | product | 11 | 0 |

- **One scenario**, tagged held-out; this design cannot speak to generalization. **n=8** per runtime and arm is not a statistically powered sample; the primary metric is not at ceiling in every group, and at this n no test of significance is claimed.
- **Effort labels.** Both runtimes request `high`, through two mechanisms; equal labels do not imply equal compute, latency or quality.
- **The skill is older than the command.** The skill snapshot is the `v0.15.0` commit; `kmp-test` runs from the deployed `0.16.0` checkout. Both are fixed for the whole campaign.
- **`success` can under-count test commands written as a chain** (`kmp-test doctor && kmp-test parallel`) **or with a leading assignment** (`FOO=1 ./gradlew test`). Key facts, the cross-arm metric, is unaffected. The campaign summary reports `success` for the product arm only.
- **Cost** is a token-based list-price estimate for both runtimes. Codex CLI's uncached input is priced as a range (input rate to cache-write rate), because OpenAI's pricing page says input tokens are either input, cached input or cache write and Codex's usage event never says which; Claude Code's estimate is a range between the five-minute and the one-hour cache-write rate.
- **Inherited from Evidence2 and Evidence1, not re-audited in depth**: Codex's `model_resolved` is an echo, not an observation; no dated model-snapshot pin exists for either runtime; the `cache_state` label is a literal.

## Limitations

A condensed restatement of Threats to validity: one scenario only; n=8 per runtime and arm, not statistically powered; effort labels matched at `high` but not claimed equivalent across products; a descriptive within-arm cross-runtime comparison that excludes `num_turns`, tool calls and tool output; cost estimated from tokens for both runtimes; the ground truth on the guest with detection by scan as the only control (0 hits); 3 infra-flake cells, a result the original stop threshold of 3 would have stopped on and the threshold of 6 set by amendment A2 before the campaign did not; one re-run after a failed first attempt, decided without looking at any result (amendment A4); two sessions missing, both in the free arm, one lost to a failed guest call under amendment A5, so those arms count 7 sessions; Codex CLI agent-state and SQLite limits (amendment A3); Windows only; and the harness records what it asked from the providers, not what they honored.
