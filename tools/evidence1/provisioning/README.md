# Evidence1 Windows provisioning

This directory defines the versioned Windows/Hyper-V base used by Evidence1. It is intentionally separate from harness deployment, authentication, network sealing, paid inference, and evidence publication.

## Safety contract

- The product VM identity is fixed by `evidence1-windows-hyperv-v1.json`. A separate closed `evidence1-windows-hyperv-e2e-v1.json` namespace exists so creator E2E never targets or overwrites `Evidence1-Runner`.
- The private input lock only supplies local paths. All hashes, sizes, upstream identities, publishers, verification methods, and Windows image metadata come from a reviewed public manifest under `approved-inputs/` that is clean and byte-bound to the current Git `HEAD`.
- Creation refuses an existing VM or directory. It never replaces or deletes either one. A partial failure is reported as a mutation that requires operator inspection.
- Scripts do not open VMConnect, terminals, login flows, or unbounded wait loops.
- Creation leaves the VM off and its only adapter disconnected. It has no switch parameter and cannot start the VM.
- The product profile remains manual. The collision-safe E2E profile uses the canonical offline-apply path: it requires a fresh `InspectCreated` PASS and revalidates the fixed VM identity, processor, memory, firmware, TPM, storage, ISO and disconnected adapter immediately before mutation. It partitions the RAW VHDX as GPT/ESP/MSR/Windows/Recovery, applies the approved Windows 11 Pro index 6 with the separately pinned Windows ADK DISM closure, sets and reads back the recovery attributes `0x8000000000000001`, and builds UEFI boot files with BCDBoot from the applied image. It never exercises the EFI optical-disc prompt or virtual keyboard.
- The E2E host dependency is Windows ADK `10.1.26100.2454` plus its reviewed servicing update, yielding the exact x64 DISM runtime recorded by the manifest. It is not installed into the guest and is not resolved from ambient `PATH`: creator inspection and image application expand the same normalized archive, verify archive/tree/executable hashes, PE architecture, product version and the Microsoft Authenticode publisher offline, then invoke the exact absolute `dism.exe` path in a hidden bounded process. Recovery deliberately does not require the archive to remain available.
- The offline path reuses the existing current-user DPAPI-protected guest credential without copying or publishing it. Its `Unattend.xml` contains only `specialize` and `oobeSystem`, is deposited in the offline Panther directory, and is removed together with AutoLogon values after the one authorized boot. The approved Microsoft ISO remains the VM's only DVD, while firmware is changed to boot the VHD first.
- An exclusive no-overwrite authorization marker under the E2E VM custody root is created after read-only preflight and before the first VHDX mutation; the later single `Start-VM` consumes that same custody boundary. Recovery is bounded and bound to the input lock plus either the fresh inspection or that marker, addresses the VM by the attested ID, and preserves only custody hashes. It recursively removes bounded `*unattend*.xml` caches from Panther, Sysprep and the setup staging Panther tree, clears AutoLogon, turns off only the fixed VM, unmounts only its VHDX and approved source ISO, leaves networking disconnected, and emits a sanitized terminal receipt. Missing provider telemetry is recorded as `null` with an explicit reason rather than inferred.
- Bootstrap copies no authentication state and performs no network access or inference. Codex and Claude get dedicated empty state roots before either CLI is probed.
- The toolchain checkpoint is created only while the VM is off. It requires a fresh `Verify` receipt bound to the exact profile, input lock, VM ID, guest SID, environment, artifact identities, and installed trees; those trees and the configured auth-store catalogue are then checked again from a read-only VHD mount. It never replaces an existing checkpoint.
- Operation receipts are collision-safe/no-overwrite. An explicit existing receipt path is rejected rather than overwritten; downstream markers and receipts bind custody records by hash.

## Artifact contract

The six guest inputs are normalized archives: Git, Node/npm, JDK, Android SDK, Claude Code, and Codex CLI. Their archive root becomes the versioned runtime root, so `command_relative` and any `required_files` from the profile must exist directly after extraction. The Codex input is the exact `codex.exe` extracted from the pinned official platform-specific npm package; its npm integrity and source-package size are recorded in the approved manifest, while input-lock creation also requires a valid OpenAI Authenticode signature. Bootstrap re-hashes every approved artifact inside the guest before installation and records resolved versions without persisting command output.

The E2E profile additionally has one host-only normalized dependency, `windows-adk-dism`. Manifest schema v2 and input-lock schema v3 add that binding without changing historical manifest v1/input-lock v2 acceptance for the product profile. The normalized ADK closure records both official upstream downloads independently and contains only the files required by DISM; receipts expose identities and versions, never source paths or raw command output.

The expected toolchain is Git for Windows `2.55.0.windows.5`, Node `24.19.0`, Eclipse Temurin `21.0.12.1+1`, Android platform 36/build-tools `36.0.0`, Claude Code `2.1.238`, and Codex CLI `0.153.4`. npm travels inside the Node closure. Gradle caches, scenario sources, and the harness remain in their dedicated Evidence1 phases.

**Known base-vs-launch gap (documented limitation, not yet resolved by a new approved-inputs version):** this base profile's own approved manifest is a versioned historical record of how the VM was actually first provisioned, and stays at Codex CLI `0.153.4` -- rewriting it to a later version here would falsify that record. The live campaign launch path pins a newer version, `0.154.0` (`evidence1-dual-condition-canary-launch.ps1:330`, `$ExpectedCodexVersion`). The currently-running VM reached `0.154.0` through a separate, already-executed, pinned in-place upgrade (`evidence1-hyperv-upgrade-canonical-codex-cli-direct.ps1`), not through this base profile. That upgrade's own required input -- a multi-file directory-layout archive matching its `$requiredRelativeFiles` shape, distinct from this profile's single `codex.exe` artifact shape -- is not yet produced by any committed, reviewed builder script; it exists only as a one-off local artifact from when the upgrade was run. A fresh VM provisioned from this base profile alone would therefore still need that same in-place upgrade step applied afterward to reach the version the launch path expects. Scripting that upgrade-input construction (and the approved-inputs v3 / profile e2e-v2 versions needed to pin `0.154.0` as a base input in its own right) is tracked in `BACKLOG.md`.

No production manifest is fabricated from arbitrary local files. Until the real Microsoft ISO and every normalized toolchain input have been acquired, independently verified, and committed as an approved path-free manifest, lock creation and `Validate`/`Create` fail closed. This is an intentional readiness gate, not a fallback.

## Phase boundaries

1. Review and commit a path-free manifest conforming to `evidence1-windows-approved-inputs.schema.json`; `evidence1-new-input-lock.ps1` then creates a private path lock plus sanitized receipt. The product profile continues to use manifest v1/lock v2, while the E2E profile requires manifest v2/lock v3 with its host-only DISM archive.
2. `evidence1-windows-vm.ps1 -Mode Validate` verifies every input without elevation or mutation.
3. `evidence1-windows-vm.ps1 -Mode Create` creates the VM after the exact authorization phrase and copies the verified ISO into its private VM directory.
4. For the product profile, an operator installs Windows 11 Pro x64 and creates the fixed local guest identity; this remains a formal manual boundary. For the separate E2E profile, `evidence1-apply-windows-offline.ps1` applies the pinned Pro image directly to the RAW VHDX, writes only the specialize/OOBE answer file, boots the VHD once, verifies it over PowerShell Direct, removes setup material, and turns the VM off. It cannot target the product profile. The older optical-boot unattended script is retained only for historical receipts and is not accepted by the E2E profile boundary.
5. `evidence1-post-os-transition.ps1 -Mode Verify` attests edition, architecture, computer/user/SID, administrator membership, PowerShell Direct, VM ID, and disconnected network. `-Mode Seal` has its own authorization and ejects the ISO without starting/stopping the VM.
6. `evidence1-bootstrap-toolchain.ps1 -Mode Bootstrap` installs the locked artifacts over disconnected PowerShell Direct. `-Mode Verify` is read-only, must report `changed:false`, and detects drift.
7. With the VM off, `evidence1-checkpoint-toolchain.ps1` independently rechecks the fresh Verify receipt, installed trees, and empty auth stores before creating the no-credential checkpoint.
8. Interactive provider login, a separately authorized remote auth canary, network resealing, harness deployment, dry-run gates, and live execution happen afterward through the existing Evidence1 operations layer.

`Create` requires `authorize create evidence1 windows vm from verified inputs`. The canonical E2E offline apply requires `authorize exactly one evidence1 e2e windows offline apply`; it authorizes exactly one start only after the complete offline image, boot, custody, and isolation gates pass. It does not authorize a retry, replacement, respawn, network access, login, inference, or deletion. Post-OS sealing requires `authorize seal evidence1 windows post-os boundary`. The checkpoint requires `authorize checkpoint verified evidence1 toolchain without auth`. None of these phrases authorizes another boundary.
